# Step 1.12 ADR handoff

For the session that runs `/adr 1.12`. Written by the session that was asked to run `/step 1.12`, found a gap and stopped before changing anything. Nothing for 1.12 has been built or written yet.

## Why there is an ADR session

The phase file (`docs/phases/01-core.md`) marks 1.12 as a plain Sonnet build with no ADR. That was a planning miss: the step needs a design decision no accepted ADR makes. CLAUDE.md lists that as a stop condition. Anthony chose to write the ADR in a fresh session first, then build.

Do not treat this as "1.12 was mislabelled, so change the scope". The scope in the brief is right. It lacks a design.

## What is missing (verified in the repo)

1. **The core has no way to emit events.** ADR 0002 says "the core emits through an `EventSink` trait the host implements". But `EventSink`, `Notice` and `CoreEvent` live in `crates/fc-api/src/notice.rs`, and `fc-api` depends on `fc-core`. The core cannot call a trait from a crate that depends on it. So the core needs its own event type and listener, and `fc-api` converts them to `CoreEvent`. Nobody has designed that.
2. **Delivery today is per call.** `OpContext::with_sink` gives a sink to one call. A merge, or a Phase 4 background sync, has no call to hang events on. Hosts: `apps/native/src-tauri/src/hub.rs` (`NoticeHub`), `crates/fc-wasm/src/lib.rs` (`JsSink`).
3. **"Study session started and ended" has no definition.** The core has no session concept. Nothing says what a session is, who starts or ends it, or what it records.
4. **The delivery rules are unwritten:** when events fire relative to the commit, what a no-op emits, what a merge emits, what a listener may do.
5. **`CoreEvent` has one placeholder variant** (`Debug`), used only by the debug-only `debugEmitEvent`. The 0.3b notes in ADR 0002 say the debug methods are deleted "when real long methods arrive (1.12)". Check whether that is still true: `debugSlow` and the others are the only way to test progress and cancel, because no real long method exists yet.

## What the ADR should decide

Write it as **ADR 0009**, status **Proposed**. Keep it short: the decisions, the options considered, the consequences, what would make us revisit it.

Starting point from the stopped session. It is a proposal to test, not a decision:

- A plain `fc_core::events` module: an `Event` enum (`#[non_exhaustive]`) and a `Listener` trait. `Core` owns the listener list and gives each `Collection` a handle on open. A standalone `Collection` (CLI, tests) has its own.
- Events are delivered after the transaction commits, on the calling thread, one batch per operation. A failed write emits nothing. A no-op (deleting a deleted note, an edit that changes no field) emits nothing.
- Events carry IDs and small facts only, never card or note content (card content is untrusted).
- Candidate events: `NoteAdded`, `NoteEdited` (with changed field IDs), `NoteDeleted`, `NoteRestored`, `CardAnswered`, `AnswerUndone`, `StudySessionStarted`, `StudySessionEnded`, `MergeApplied` (one summary with counts, built from `MergeReport`, not one event per note), `SyncCompleted` (stub).
- Study sessions: explicit `start_study_session(deck?)` and `end_study_session(id)`, held in memory, counting answers made while open. Open question for the ADR: is that the right model, or should session events wait for Phase 2?
- `fc-api` gets the real `CoreEvent` and a `forward_events(core, sink)` function that hosts call once at startup.
- Listener rules: return quickly and never call back into the core (the collection lock is held), and clients ignore unknown event kinds. Check what happens to a panicking listener, especially on wasm, before writing anything about it.

The ADR must also state what is out of scope. The stopped session proposed: hooks that can change a result (Phase 10), events for deck, tag, suspend and media writes, and new CLI commands.

## Constraints from later steps

Do not let this ADR make these harder.

- **Phase 2.3 (review screen)** has a "Session end screen". It will be one of the first users of the session events, so the session model should fit what that screen needs. Read `docs/phases/02-study-loop.md`.
- **Phase 4 (sync)** needs `SyncCompleted` to exist. Phase 4 emits it for real. The ADR should say how.
- **Phase 10 (add-ons)** gets a narrower surface, not the UI's one (ADR 0002, "Revisit if"). Events with no card content make that filtering possible. Do not design the add-on API now.
- **1.13 (backup) and 1.14 (CLI)** do not depend on events. Nothing in the ADR should require changes to them.
- **ADR 0008** (merge, built in 1.11a, PR #25): `Collection::merge` returns a `MergeReport`. Reuse it. Do not change merge behaviour.
- **ADR 0002**: do not edit it. It stays as it is. If the new ADR changes one of its sentences (the one about the core emitting through `EventSink`), say so in ADR 0009's "Context" or "Consequences" and let Anthony decide whether to add a pointer later.
- API types follow ADR 0002: camelCase, no 64-bit integers, UUID strings for IDs.
