# Plan: step 2.1 App shell and design direction

Builds ADR 0010 once Accepted, on ADRs 0002 and 0005. Model: Sonnet build (`/step 2.1`). Use the
visual direction and type option Anthony picked in his review. The placeholders below say `<chosen>`.

## Size and split

One PR, about 1,300 lines including CSS and tests. Commit in the order below, so 1 to 6 (pure UI)
can be reviewed apart from 7 (native). If it heads past 1,600 lines, stop and propose moving 7 into
its own PR (2.1b).

## Steps

1. **Tokens and base styles** (`packages/ui/src/styles/`):
   - `tokens.css`: the `<chosen>` palette as custom properties for light (`:root`), dark
     (`@media (prefers-color-scheme: dark)` on `:root:not([data-theme="light"])`) and
     `:root[data-theme="dark"]`. Also spacing scale, type scale in `rem`, radius, focus ring,
     motion (off under `prefers-reduced-motion`), and `color-scheme`.
   - `base.css`: a small reset, body font and background, focus-visible ring, `.visually-hidden`.
   - `index.ts` imports both, so each app gets them by importing `ui`. Delete both apps'
     `styles.css`. Move the spike styles to a `spikes.css` used only by the Developer screen.
2. **Theme** (`packages/ui/src/theme.ts` plus a small hook):
   - `ThemePreference = "system" | "light" | "dark"`, read and written with `localStorage` key
     `fc.theme` (try/catch, default `system`).
   - It sets `data-theme` on `<html>` (removed for `system`), listens to
     `matchMedia("(prefers-color-scheme: dark)")`, and calls `platform.setSystemTheme(effective)`
     on every change of the effective theme.
   - `apps/native/public/theme-boot.js` and `apps/web/public/theme-boot.js` (one source: put it in
     `packages/ui/public-shared/` and have each Vite config copy it, or keep two identical
     three-line files and a test that they match; pick the simpler and say which in the notes). It
     reads the same key and sets `data-theme` before first paint.
   - `<script src="/theme-boot.js"></script>` in both `index.html` heads. No inline `<style>` or
     `style=""` anywhere in `index.html` (ADR 0010 finding 4).
   - Viewport meta in both: `width=device-width, initial-scale=1, viewport-fit=cover`.
3. **Router** (`packages/ui/src/router.tsx`): about 100 lines.
   - Routes: `decks`, `add`, `browse`, `settings`, `settings/developer`, `study/:deckId`
     (placeholder screen for 2.3). Hash URLs. Unknown hash goes to `decks` with `replaceState`.
   - `navigate(path)` uses `pushState` (or a hash assignment), `back()` uses `history.back()`. It
     listens to `popstate` and `hashchange`.
   - After a route change: focus the page `h1` (`tabIndex=-1`) and set `document.title` to
     `"<Page> · Flash cards"`.
4. **AppShell** (`packages/ui/src/shell/`):
   - `AppShell` renders the bottom bar (under 600 px) or the rail (600 px and over, label beside
     the icon from 1024 px) from one `destinations` list (id, label, icon, route, shortcut key),
     plus `<main>` with the page content. Full-screen routes (`study`) render without navigation
     and with a back control.
   - Insets: CSS `env(safe-area-inset-*)` on the header area, bottom bar, rail and content. No
     inset maths in screens.
   - Keyboard: a `useKeyboardInset` hook on `visualViewport` `resize` and `scroll` writes
     `--keyboard-inset` on the shell root. While it is above 0, hide the bottom bar and pad the
     content. A `BottomAction` slot component that sits above the keyboard (used from 2.4; add one
     on the Developer screen to test it).
   - Shortcuts (600 px and over or any physical keyboard): `g` then `d`, `a`, `b`, `s`. `?` opens a
     small shortcuts list (a `dialog` element). Ignore keys while an `input`, `textarea`,
     `select` or `contenteditable` has focus.
   - Icons: inline SVG components drawn for the direction (Decks, Add, Browse, Settings, Back,
     Developer, Warning, Empty), `aria-hidden`, with labels always visible in the navigation.
5. **Screens for this step:**
   - `EmptyState` (icon, sentence, optional button).
   - Decks, Add and Browse: a page title plus an `EmptyState` saying what arrives in which step,
     in plain words ("Your decks will appear here."). 2.2, 2.4 and Phase 3 replace them.
   - Settings: an "Appearance" group with System, Light and Dark as a radio group, and the
     "Developer tools" row in debug builds (step 6).
   - **Collection problem screen**: `AppShell` calls `getCollectionInfo` once at start. On
     `updateRequired`, `unavailable` or another error it shows the full-screen message from
     ADR 0010 decision 6 instead of the destinations. Test each kind with `createFakeTransport`.
   - Remove `CoreVersion` and `CollectionStatus` from the root. Show the core and collection
     versions on the Developer screen instead.
6. **Developer screen** (`settings/developer`): hosts `DivideForm`, `SchedulingSpike`,
   `CardSandboxSpike` and, on the web, the `SpikePanel` and `BackupPanel` passed in from
   `apps/web` through an `extraDeveloperTools` prop on `App`. Visible when
   `import.meta.env.DEV || import.meta.env.TAURI_ENV_DEBUG === "true"`. Add
   `envPrefix: ["VITE_", "TAURI_ENV_"]` to `apps/native/vite.config.ts`. Check the value really
   arrives in `bun run android:build` (ADR 0010 says this is unverified).
7. **Native: system bars and title bar follow the theme.**
   - `Platform.setSystemTheme(theme: "light" | "dark"): void` in `packages/ui/src/platform.tsx`.
     Web: update `<meta name="theme-color">` to the `bg` token. Fakes in tests record calls.
   - `fc-native`: a fifth command `set_system_theme(token, dark: bool)` with the token check.
     Desktop: `webview.window().set_theme(Some(Theme::Dark | Theme::Light))`. Android: call the
     plugin below. Add it to `generate_handler!`, `build.rs` / `AppManifest::commands`, the
     autogenerated permission and `capabilities/default.json`, like the other four. Extend the
     test that every command rejects a missing token.
   - A local plugin in `lib.rs`: `tauri::plugin::Builder::new("appearance")` whose `setup`
     registers `register_android_plugin("dev.placeholder.flashcards", "AppearancePlugin")` on
     Android and stores the `PluginHandle` in managed state. No `invoke_handler`, no permissions.
   - `gen/android/app/src/main/java/dev/placeholder/flashcards/AppearancePlugin.kt`: a
     `@TauriPlugin` class with one `@Command setBarStyle` that reads `{ lightBars }` and sets
     `isAppearanceLightStatusBars` and `isAppearanceLightNavigationBars` on the UI thread. The
     probe version of this file worked as written (ADR 0010 finding 5). Mind the package name if
     the bundle ID changes before 2.7.
   - The Tauri transport module exposes `setSystemTheme` (it holds the token), and
     `apps/native/src/main.tsx` puts it in the `Platform` object.
8. **`fc-api`: keep the open error.** `Core` records the `ApiError` from a failed
   `open_collection`, and the "No collection is open." error is replaced by it while it is set.
   `fc-native`'s `open_collection` keeps the error instead of a string (still logs it). Tests in
   `fc-api`: a collection from a newer schema gives `updateRequired` from `getCollectionInfo`.
9. **Tests (Vitest, happy-dom):**
   - Contrast: parse `tokens.css`, compute WCAG ratios for text, muted, accent, danger and
     on-accent (4.5:1) and control (3:1) against bg and surface, in light and dark. Fail with the
     pair and the ratio.
   - Theme: preference storage (including a throwing `localStorage`), `data-theme` set and
     removed, `setSystemTheme` called on override and on a system change.
   - Router: navigate, back via `popstate`, unknown route, focus moves to the `h1`,
     `document.title`.
   - Shell: `aria-current` on the active destination, `nav` labelled "Main", shortcuts (and
     ignored inside a text field), keyboard inset hides the bar (mock `visualViewport`).
   - Collection problem screen for each error kind.
   - `theme-boot.js`: run it against a fake `localStorage` and check `data-theme`.
