# Plan: step 0.7 Data model and sync strategy (handoff to Phase 1)

Step 0.7 is design only, so there is no build session for it. This plan says how Phase 1 builds
ADR 0006 (Accepted).

## Change to the phase plan (agreed, see ADR 0006, "Decisions on review")

ADR 0006, section 13, needs change tracking from the first table onwards. `phases/01-core.md` used
to put it all in step 1.11. Now:

- **1.1a** builds collection storage and migrations. **1.1b** builds the sync foundation:
  - IDs;
  - the host `Clock`;
  - the HLC;
  - the device ID;
  - the register clock table and the single write path;
  - the unknown-data store;
  - collection-level `requires`.
- **1.2 to 1.10** use that foundation for every synced table they add.
- **1.11** becomes:
  - an Opus design pass on the details (wire-neutral change records, superseded-values log, purge);
  - the merge function;
  - the two-collection tests for every edge case in ADR 0006, section 11.

## What each Phase 1 step must include

- **1.1a and 1.1b.** 1.1a: collection create, open, close and migrations. 1.1b: the rest of this item.
  - `Clock` trait supplied by the host: `fc-native` uses `SystemTime`, `fc-wasm` uses `Date.now()`
    and `getTimezoneOffset()`.
  - UUIDv7 IDs from `uuid` (direct dependency, `v5` feature only) and `getrandom`. Test in the
    browser that `getrandom` works there (checked only under Bun in 0.7).
  - The HLC, saved in the collection.
  - The device ID, with the installation ID kept outside the collection. A test that a copied
    collection gets a new device ID.
  - The register clock table and the write path, with a test that every synced table is registered.
  - The unknown-data tables. Collection `requires` checked on open.
- **1.2 Note types.** Field and template IDs. Built-in note types with fixed IDs. Position registers
  with ties broken by ID.
- **1.3 Notes and cards.** Field values keyed by field ID. Card IDs from UUIDv5 (note, template,
  ordinal). Cards no longer generated are soft-deleted, and regenerating them restores them. No
  unique constraints. Duplicate detection is a warning only (already the brief).
- **1.5 Decks and options.**
  - The Default deck and default preset have fixed IDs.
  - Deck delete writes tombstones for its cards.
  - Read-time rules: a deleted deck with live cards stays alive, cycles are broken by the newest
    parent change, duplicate names are allowed.
  - FSRS parameters are one register.
- **1.6 Tags.** One (note, tag) register per tag. Renaming a tag rewrites the affected registers.
- **1.7 Study queues (its own Opus ADR).**
  - Card events (review, set due, reset, reschedule, void) with recorded inputs, result, previous
    event and fuzz seeded from the event ID.
  - The scheduling cache is derived by the fold in ADR 0006, section 4. Undo writes a void event.
  - Events record UTC time and UTC offset.
- **1.8 History and stats.** Read from events, skipping voided ones. Statistics and optimisation
  include reviews of deleted cards.
- **1.10 Media.** SHA-256 identity (`sha2`, already in the lockfile), hash-derived names, media file
  entity with registers. A referenced file is never treated as unused.
- **1.11 Change tracking.** The merge function (registers and events, HLC advance, cache recompute).
  Tests that merge two collections for every row of ADR 0006, section 11 that does not need a server.
- **1.13 Backup and restore.** Restore writes the difference as new changes, with a new device ID.
  The export format includes IDs, clocks and events.

## Review focus for the Phase 1 PRs

- Any write to a synced table that skips the write path.
- Any `UNIQUE` constraint, foreign key or counter on a synced table.
- Any hard delete outside purge.
- Any scheduling field written other than by the fold.
