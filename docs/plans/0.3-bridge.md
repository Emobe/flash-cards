# Plan: step 0.3 UI-to-core bridge

For the build session (`/step 0.3`). Builds ADR 0002 once it is Accepted. Do not start before then.

## Proposed split

Two PRs, each one coherent change:

- **0.3a Call path.** Everything the acceptance criteria need: one example call, errors, type sync,
  on desktop and phone.
- **0.3b Notices, long operations, attachments.** The rest of the `Transport` interface, so step 0.4
  can implement and test the full interface on the web. No real domain functions. It could wait
  until it is first needed (1.12), but then 0.4 would validate an interface that is only half built.
  Recommended before 0.4.

## 0.3a Call path

1. **`crates/fc-api`** (new crate, picked up by the `crates/*` glob): `Method` trait, `ApiError` and
   `ErrorKind`, `OpContext` (with `checkpoint` only for now), the method-list macro generating
   `dispatch` and the `Methods` map. Dependencies: `fc-core`, `serde`, `serde_json`, `ts-rs = "=12.0.1"`.
2. **Example methods** (temporary, deleted when real methods arrive):
   - `getCoreInfo() -> { coreVersion }`, from `fc_core::version()`.
   - `exampleDivide({ dividend, divisor }) -> { quotient }`, computed in `fc-core`. Dividing by zero
     returns `invalidInput` with the message "Can't divide by zero. Enter a divisor other than 0."
3. **Bindings test** in `fc-api`: generates into memory with the large-int sentinel, compares with
   `packages/core-client/src/generated/`, fails with "TypeScript bindings are stale: run
   `cargo xtask bindings`". Writes the files when `FC_UPDATE_BINDINGS=1`. Never use `#[ts(export)]`
   (it writes files during every `cargo test`).
4. **`cargo xtask bindings`**: runs that test with the variable set, then `biome format` on the
   generated directory so `check` stays clean. Update the xtask usage text and `README.md`.
5. **`packages/core-client`** (new): `Transport`, `CoreClient` (`call` and `CoreError` only in 0.3a),
   `createFakeTransport`. Vitest project for it.
6. **`fc-native`**: `call` command (async, `spawn_blocking`, `ipc::Response` frame, `ApiError` on
   failure, panics caught and turned into `internal`). Holds the core in Tauri state.
7. **Command access**: `AppManifest::commands(&["call"])` in `build.rs`, `allow-call` in
   `capabilities/default.json` for `main` only. Verify a command not granted is rejected.
8. **CSP**: add `connect-src ipc: http://ipc.localhost` in `tauri.conf.json`.
9. **Tauri transport** in `apps/native/src` using `@tauri-apps/api` (`=2.12.1`, matching the crate).
   Frame decoder accepts `ArrayBuffer` or number `Array`. Unit tests with `@tauri-apps/api/mocks`
   (`mockIPC`), so no new test dependency.
10. **UI**: a `CoreProvider` context and a `useCore()` hook. The placeholder screen shows the core
    version and a small divide form that shows either the quotient or the error message. The form
    must use large tap targets and stay readable on the phone.
11. **ADR 0001**: answer the bindings-location assumption and list the new members.

Tests:
- Rust: dispatch of each example; unknown method gives `unknownMethod`; malformed input gives
  `invalidInput` with a readable message; `ApiError` JSON shape; bindings test.
- TS: `CoreClient` typing (a `// @ts-expect-error` test for a wrong input type), `CoreError` mapping,
  frame decoding of both shapes; UI renders a value and an error message through the fake transport.

Manual checks (in the PR):
- Desktop: value shown, divide-by-zero message shown, no "IPC custom protocol failed" warning in
  the devtools console.
- Phone: same, by screenshot. Note the Android timings of a call if easy to see.
- Type sync: rename a field in an API type, run `cargo xtask bindings`, confirm `cargo xtask check`
  fails in `tsc`, revert. Without the bindings step, confirm `check` fails with the stale message.

## 0.3b Notices, long operations, attachments

1. `Notice`, `CoreEvent` (one placeholder variant, replaced in 1.12), `Progress`, `EventSink` in
   `fc-api`. `OpContext` gains `progress` and attachment access.
2. `fc-native`: `subscribe` (one channel per webview label, replaced on reload), `cancel` (records
   early cancels), operations map, progress throttling. Base64 attachment decode, frame attachment out.
   Add the two commands to the `AppManifest` list and capability.
3. `CoreClient`: operation IDs, `signal` and `onProgress`, `onEvent`, attachment typing. Tauri
   transport: `subscribe`, `cancel`, base64 encode (`Uint8Array.prototype.toBase64` with a fallback).
4. Debug-only methods (`#[cfg(debug_assertions)]` registration) to exercise them: `debugSlow`
   (progress plus checkpoints), `debugEchoBytes`, `debugEmitEvent`. A debug-only panel in the UI, or
   tests only. Decide in the PR.
5. Tests: cancel before start, cancel mid-run, progress order, attachment round trip, event delivery
   after a re-subscribe. Measure 1 MB and 5 MB attachments on the phone and note the result in the
   ADR (Android timings are unverified).

## Out of scope

Real domain methods, media URLs (0.6), file pickers, the `Platform` interface, the web transport (0.4).
